# Shared workspaces: acceptance tests

This maps each acceptance criterion in the
[review](../audits/2026-11-08-shared-workspaces-review.md#7-acceptance-criteria)
to the automated check that covers it, the manual staging journey
([staging-setup.md](staging-setup.md#7-journeys)), or a gap. The automated
checks run locally against `convex-test` and the real Better Auth engine with
in-memory or SQLite storage. They don't prove a live Entra registration, live
SharePoint, real browsers or real mail.

## Production observations (November 8, 2026)

The shared production cutover and `portal.1stform.ca` setup are recorded in
[production-setup.md](production-setup.md). These observations supplement the
matrix; they do not imply every journey below was performed.

- A real export/rehearsal and final production transfer passed row, reference,
  file checksum and financial-total verification. Repeat apply inserted no
  duplicates. Exact new identities retained the source Owner/Admin roles.
- Both builds/TypeScript and 16 focused feature checks passed. All six checks
  on [PR #77](https://github.com/ahzs645/societyer/pull/77) passed. The existing
  notification-settings and standalone export-coverage failures were recorded
  separately; neither was the transfer verifier.
- DDC's normal rendered login remained Microsoft-only; its linking variant
  included the password form. An Owner identity without Microsoft evidence
  was locked and denied a direct workspace read. A real Microsoft session
  continued to resolve to Owner.
- The separate DDC staff admin API accepted a real Microsoft Owner JWT (200)
  and denied the real First Form password JWT (401). An initial library-default
  user-agent edge block was distinguished from application authentication.
- The First Form Owner completed password setup and real browser sign-in.
  Dashboard/Owner survived reload. **My workspaces → Open Firstform** then
  carried that session from Pages to `portal.1stform.ca/app` without another
  login; the final URL had no fragment and reload remained signed in.
- Domain/storage audits and domain-specific MCP discovery passed. Live
  third-party AI clients, request/approver mail, a new native document-version
  upload, and linked cross-organization journeys remain unqualified.

## Automated checks

| Command | Script | What it asserts |
| --- | --- | --- |
| `npm run test:workspace-sign-in-policy` | `scripts/check-workspace-sign-in-policy.ts` | Session evidence comes only from the signed `societyer_session.*` and `societyer_entra.*` claims, and mistyped or invalid proof is ignored. Deployment-wide required SSO still makes a password session anonymous. `set` refuses a wrong tenant, an unlisted or empty group, a blank reason, Microsoft fields on `any`, bad domains, a bad support email, and Entra being off or broken, and writes nothing then. A DDC Microsoft session opens DDC but not First Form. A DDC password session is refused with the Microsoft message and gets `sign-in-required` with a `microsoft` lock. Expired, wrong-tenant or wrong-group evidence is refused. A First Form password session opens First Form and not DDC. Microsoft evidence never creates a membership. A linked person's password session opens First Form and sees DDC locked; their Microsoft session opens both, each with its own role. Another identity's proof is never reused. The email-domain rule needs a verified email in an allowed domain. `clear` restores access and both changes are logged. |
| `npm run test:account-links` | `scripts/check-account-links.ts` | `begin` needs a deployment-signed session from the last 15 minutes. Codes are 43 characters, stored only as SHA-256, last 10 minutes, and a new `begin` cancels the old code. Preview shows only the two parties and their workspaces. Stale, same-account and unauthenticated attempts are refused. A confirmed code can't be replayed or reused by a third identity. Either linked session reaches the other's Active memberships with their own roles. Disabled stays Disabled. Only deployment-signed user sessions follow links: gateway, API-token, service and trusted-workspace principals don't. Overview shows only the caller's own person. An invitation accepted through a linked login adds no second membership. A forced overlap makes the workspace unreachable for both. Conflicts (Disabled memberships and already-linked people included) are refused, spend the code and are logged. Disabled identities can't begin or confirm. Expiry, cancel, merging two people, unlink, removing a one-login person and relinking. Better Auth part: no implicit linking by matching email. Explicit `linkSocial` attempts are refused; provider attachment remains operator-only. |
| `npm run test:operator-identity-tools` | `scripts/check-operator-identity-tools.ts` | `operatorInspect` shows the state, person, every linked login with its memberships, and the link events. `operatorUnlink` needs a reason, removes access through the other login, logs actor `operator` / `deployment-operator`, removes a one-login person, keeps a person with two logins left, and clears a Disabled (blocked) person so it can link again. `operatorRetireMembership` refuses a blank reason, the same row, rows in different workspaces, an inactive or retired keep, retiring twice and the last Active Owner, and changes nothing then. After retiring: the row is Disabled, unbound and `mergedIntoUserId`; the kept row and its role are unchanged; a higher retired role is reported, not carried; an activity row is written; history rows still resolve to the retired row; no identity reaches it; it can't be reactivated or invited and doesn't hold its email. The link the conflict check refused now succeeds and both logins resolve exactly the kept membership. |
| `npm run test:workspace-domains` | `scripts/check-workspace-domains.ts` | `upsert` normalizes origins and refuses paths, credentials, origins outside `SITE_URL`, missing workspaces and a second Active workspace per origin. A new primary demotes the old one. `resolveOrigin` returns null for unknown, disabled, ambiguous and untrusted origins, and otherwise only the workspace ID, name, origin, logo and sign-in method plus support email. `audit` flags ambiguous, unmapped, untrusted and multiple-primary cases. Provisioning, reset and invitation links use the canonical origin, fall back to the first `SITE_URL`, and honour `appUrl`. `installInvoiceTemplate` installs for one workspace without the deployment flag, is idempotent, and refuses a workspace without an Active Owner. |
| `npm run test:session-handoff` | `scripts/check-session-handoff.ts` | On the real Better Auth engine with the production plugins: create needs a session and a trusted app origin, refuses untrusted, non-exact and same-origin targets and calls without an `Origin`. Only the code hash is stored, with a 60-second lifetime. Redeem from the wrong origin is refused and burns the code. Success delivers the same session only through the cross-domain header, mints no new session, and can't be replayed. Expired codes, tampered rows, and expired or revoked source sessions are refused. Both endpoints are throttled per IP. The destination-held verifier is required; its SHA-256 challenge is bound to the code. Missing, malformed or mismatched verifiers/challenges and unmapped origins are refused. |
| `npm run test:workspace-storage-policy` | `scripts/check-workspace-storage-policy.ts` | No row keeps the deployment behaviour, and the deployment flag is a ceiling. `set` validation. A DDC-like SharePoint workspace is refused on every native path (upload URLs, attachments, asset and inventory images, offline meeting files, Paperless pulls, transcript storage, demo versions) and its versions go to SharePoint. A First Form-like native workspace on the same deployment uses native storage. Upload handles are bound to the provider. SharePoint broker routes refuse a native workspace before calling Microsoft. Duplicate rows refuse uploads. |
| `npm run test:shared-workspace-ui` | `scripts/check-shared-workspace-ui.ts` | Startup rules 1–4 and the unmapped fallback. The pending choice is used once and expires. Handoff `next` is limited to same-origin `/app` paths, fragment parsing, redemption strips the fragment first and selects nothing on failure. Switcher: same origin versus handoff, unsafe canonical origins ignored. `resolveOrigin` result parsing. The link code lives in `sessionStorage` and expires. Sign-in options: a Microsoft-only domain shows only Microsoft, except during a link (`?linkAccount=1` or a redirect to `/account/link[/confirm]`), when a password form is added, never while capabilities load or when the deployment requires Microsoft. The destination-initiated request, verifier/challenge, per-tab expiry and refusal of codes the tab did not request are covered. |
| `npm run test:workspace-transfer` | `scripts/check-workspace-transfer-policy.ts`, `scripts/check-workspace-transfer.ts` | Every schema table has exactly one reviewed transfer policy, credentials and per-deployment state stay skipped, and the schema walker finds required, optional, nested and array references. End to end on convex-test: a source with two workspaces is written in the Convex export ZIP layout (ZIP64 is read too). A cross-workspace reference and an unfinished sync run block the plan, also through the CLI. The plan adopts a legacy directory row, follows child rows without `societyId`, excludes tokens, grants, invitations and file claims, and reports a string that holds the ID of an excluded row. Apply into a destination holding DDC North is interrupted and resumed with no duplicates; a replayed batch inserts nothing; rows of skipped tables or of another workspace are refused; a second run for the same workspace is refused. The copy is quarantined (no public slug, no feed token, crons skip it), memberships are unbound, workflows and the vault are disabled or redacted, the meeting/minutes cycle and string-held IDs (also inside JSON and in `documentVersions.storageKey`) are rewritten, and both files are byte-identical and claimed. Verify passes, fails on a corrupted reference and on a stray row, and finalize refuses until it passes. Bind refuses before finalize, a bound row, a second membership for one login, another issuer, unknown and foreign rows, and keeps Disabled; Entra provisioning refuses a quarantined workspace and binds the imported row (matching email) instead of adding a Viewer; the bound owner opens the workspace and not DDC. A second run aborts and removes only its own rows. DDC rows stay byte-for-byte unchanged throughout. |
| `npm run test:workspace-selection` | `scripts/check-workspace-selection.mjs` | Per-tab selection, plus: selections remembered per backend URL, and no first-workspace fallback on a mapped origin. |
| `npm run test:access-requests` | `scripts/check-access-requests.ts` | Requests are off by default and `availability` then returns only `{ enabled: false }`. A workspace without an Active, trusted domain reveals nothing even with requests on, nor does any call without a deployment-signed session. Settings are Owner/Admin only, with a Viewer or Member default and a 500-character message. Submit needs a verified email, trims the note, stores the session's exact issuer and subject, returns the existing pending request on a repeat, and notifies only the Active Owner and Admin (email recipients checked). Withdraw works only for the identity that asked. A member, a Disabled member and a person whose linked login is a member are refused. Five requests per 24 hours. Non-members, Viewers and a foreign workspace's Owner can't list, approve or decline. An Admin can't grant Admin, nobody grants Owner, an Owner grants Admin. Approval binds exactly the requester, who can then open the workspace while nobody else can; re-decisions are refused. Decline. Approval re-checks a later membership, a Disabled identity and an email already in the roster. Turning requests off hides them again. A password session approved into a Microsoft-policy workspace is still locked (`sign-in-required`, `microsoft`) and its Microsoft session opens it. |
| `npm run test:mcp-oauth-origins` | `scripts/check-mcp-oauth-origins.ts` | With `SITE_URL` listing two origins: each origin's AI connector URL (`<site>/mcp/<host>`) has its own protected-resource metadata and `401` challenge, its sign-in lands on that origin's `/oauth/consent`, and the completion is refused (and logged, request unchanged) from the other trusted origin or an untrusted one. Unknown, extended or encoded hosts are `404` or `invalid_target`. No `resource`, `/mcp` and the bare issuer still use the first origin; `SOCIETYER_MCP_OAUTH_CONSENT_URL` still wins. A token bound to `/mcp/<host>` works only there. Settings shows the URL for the origin it's on. |

Run all of them, plus the related existing suites:

```sh
npm run test:workspace-sign-in-policy && npm run test:account-links && npm run test:operator-identity-tools && npm run test:workspace-domains \
  && npm run test:session-handoff && npm run test:workspace-storage-policy && npm run test:shared-workspace-ui \
  && npm run test:workspace-selection && npm run test:access-requests && npm run test:hosted-entra && npm run test:identity-binding \
  && npm run test:workspace-access && npm run test:workspace-mfa && npm run test:document-upload-binding \
  && npm run test:sharepoint-connection && npm run test:stage2-tenancy && npm run test:multi-user-pipeline \
  && npm run test:mcp-oauth && npm run test:mcp-oauth-origins \
  && npm run test:workspace-transfer
```

Each script is `tsx scripts/<name>` (or `node` for the `.mjs`). You can run it
directly with `./node_modules/.bin/tsx scripts/check-….ts`. The stage-two
harness reports blocked, error and not-applicable outcomes. A harness error is
not a passed isolation check.
